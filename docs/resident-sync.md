# 常驻服务：内存快照与事件驱动同步

此 fork 增加了适合常驻服务的可选同步模式，不改变原有工具名称。默认仍使用原来的磁盘快照模式；短连接 stdio 客户端继续使用默认模式。

## 启用

使用支持 `sqlite3.Connection.deserialize` 的 Python 3.11+，安装项目的 `wechat,watch` extras。在服务进程环境中设置：

```text
WECHAT_SYNC_MODE=memory
```

沿用初始化时的密钥与源数据目录。通过现有的 `set_auto_sync(enabled=True)` 开启后台同步；关闭时同样调用 `set_auto_sync(enabled=False)`。无需重新获取密钥。安装或迁移应在停服后完成。

内存模式下，旧的 `interval_minutes` 设置仅为兼容保留，不控制更新延迟。系统文件通知触发同步，静默合并窗口为 0.3 秒、最长合并等待 2 秒。每 300 秒另做一次完整复核；如果未安装 watchdog 或通知线程退出，则退回 5 秒检查文件元数据。文件通知只表示“可能有变化”，不代表一条新消息已经收到。

Windows 使用 watchdog 的 `ReadDirectoryChangesW` 后端。文件通知可能丢失，因此保留低频复核。原始数据目录与数据库只有读取操作。

## 同步流程

1. 检查每个源 `.db` 和对应 `-wal` 的文件身份、大小、时间和头部；定期完整复核以覆盖元数据不变的情况。
2. 仅重新读取、解密变化的分库。逐页检查 HMAC；验证 WAL 头、代次盐和帧校验和，只应用有效前缀中的已提交事务。不依据“日志页数小于主库”推断 WAL 过期。

   包含微信专用 `MMFtsTokenizer` 的库无法由标准 SQLite 执行虚拟表全库检查；遇到明确的扩展缺失错误时，改为逐个检查普通表及影子表。其他损坏或 I/O 错误仍导致更新失败。
3. 读取前后检查源文件状态；存在并发变化时重试，无法确认时保留上一轮结果。该机制是对活跃文件的乐观捕获，不能替代微信/WCDB 本身提供的事务快照 API。
4. 候选快照在内存中经 SQLite 检查后，只扫描变化的分库；联系人变化时也刷新会话名称。已有消息仅字段不同才更新，避免无效 FTS 更新和自增序列增长。
5. 查询索引及消息事件在同一 SQLite 事务中更新。成功后发布内存快照；失败则回滚索引，保留上一版内存快照。查询原始转发内容和图片资源映射也从内存快照读取。

内存模式不会覆盖或自动删除以前生成的解密文件，也不再使用这些文件作为同步或原始消息查询的数据来源。回退磁盘模式前，应在停服后用原有初始化/同步流程更新磁盘快照，避免查询旧数据。

首版仍完整读取、解密一个发生变化的分库，尚未实现跨轮次页级增量解密；优化重点是减少磁盘写入。单个输入文件上限 512 MiB，快照有效负载总量上限 1 GiB；SQLite 反序列化和候选代次会带来额外内存占用。这些上限不是进程 RSS 上限。内存也可能由操作系统换页，不承诺明文绝不落盘。

## 下游事件接口（预留）

当前没有 HTTP 接收端、webhook、脚本执行器或自动网络发送。只提供进程内 Python 接口，方便后续实现选定的下游适配器：

```python
from wechat_mcp.events import wait_for_events, acknowledge_events

batch = wait_for_events(timeout=60, limit=100)
for event in batch:
    # adapter.handle(event) 由后续下游适配器实现
    # 操作成功后再确认；失败则保留，重启后仍可重试。
    pass
# acknowledge_events([event["id"] for event in successfully_handled])
```

`pending_events(limit)` 提供非阻塞读取；`wait_for_events` 在同一进程内通过通知唤醒，不需要反复查询数据库。跨进程或跨主机接入需要后续适配器。

事件包含本地递增 `id`、随机唯一 `event_id`、`kind`、`message_id` 和 `created_at`。类型为 `message.created`、`message.updated`、`message.deleted`。不在事件中复制聊天正文、联系人名或源文件路径。查询索引本身仍包含原有明文数据，事件表与其使用同样的访问控制。

初次建立基线不发送整段历史；后续新增记录（包括历史补充）、修改和删除会生成事件。这些是“索引消息变化”，包括本机发送的消息，不能直接等同于“收到一条新消息”；后续适配器需明确会话、方向与历史补充的过滤策略。

事件表仅在成功提交后对消费者可见。消费为至少一次语义，接收方用 `event_id` 去重，再调用 `acknowledge_events(ids)` 确认。当前只预留一个逻辑消费者；多个消费者需要各自确认游标。`prune_events(before_timestamp)` 可显式清理已经确认的旧事件，未确认事件不会自动丢弃；长期无人消费时需关注队列增长。

## 行为与边界

- 微信退出：源文件没有变化时保持空闲，最后一次成功索引仍可查询。微信重新登录并写入源文件后触发更新。
- 服务重启：从加密源库恢复内存快照，已有查询索引与未确认事件保留；重复同步不重复生成事件。
- 新分库缺少密钥、源文件持续变化、HMAC 不通过或解析失败：更新失败且保留旧结果。新增分库可能需要重新初始化密钥。
- 当前内存模式仅支持微信 4.x 的目录布局；其他布局请继续使用默认模式。
- 对发生变化的消息分库进行完整键集合核对，反映原记录删除；整个分库消失也会移除其索引消息。不要把索引用作历史归档备份。
- 证书、HTTPS 服务包装、自启动和进程恢复不属于该模式的配置范围，沿用现有部署。

```sh
python -m unittest discover -s tests
```

新增测试只使用合成 SQLite/WCDB 数据，覆盖认证解密、WAL 提交边界和旧尾部、空闲无索引写入、消息新增/修改/历史补充/删除、FTS、失败回滚、重启去重、原始内容读取和文件通知。
